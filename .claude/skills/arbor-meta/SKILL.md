# Arbor Meta

This skill is for local Arbor users who have already run `arbor init` in a project. After reading it, an AI should understand the Arbor architecture, operating model, and customization entry points inside that user project, then modify the generated files according to the user's request.

In Arbor the eight roles (explore, architect, test, implement, review, verify, fix, simplify) are not platform sub-agents. The driver, `.arbor/scripts/arbor.py`, runs them through the executor configured under `executors:` in `.arbor/config.yaml`; the main agent writes the contract and the briefs and follows `arbor.py next`. Role instruction text lives in `.arbor/agents/*.md`.

The default operating scope is local files in the user project:

- `.arbor/`: workflow, config, tasks, spec, workspace, scripts, assistant instruction sources (`agents/`), and runtime state.
- Platform directories: `.claude/` (Claude Code) and `.starFactory/` (StarFactory, a Claude Code fork whose project config dir is `.starFactory/`, not `.claude/`).
- Root files `CLAUDE.md` and `AGENTS.md`, each with a managed block between `<!-- ARBOR:START -->` and `<!-- ARBOR:END -->`.

Do not assume the user has the Arbor source repository. Do not default to modifying the global npm install directory or `node_modules`.

## How To Use

1. Read `references/local-architecture/overview.md` first to establish the local Arbor system model.
2. If the request involves the driver, running roles, executors, the dispatch header, briefs, or task worktrees, read `references/local-architecture/dispatch.md`.
3. If the request involves hooks, settings, skills, or commands, read the relevant `references/platform-files/` note.
4. If the user wants to change behavior, read `references/customize-local/overview.md`, then open the specific customization topic.
5. Before editing, read the actual files in the user project and treat local content as authoritative.

## Current Rules

- `.arbor/workflow.md` is the local workflow source of truth.
- `.arbor/config.yaml` is the project-level configuration entry point: task lifecycle hooks (`hooks.after_*`), journal shape, packages, `context_injection` limits, `prompt_injection.skip_keyword`, `executors:` (how the driver runs a role: command, timeout, `max_parallel`), `gate.commands` (project-wide GATE checks), `worktree:` (task worktree root and setup command), and `test_paths:`.
- `.arbor/spec/` stores project-specific coding conventions and design constraints.
- `.arbor/tasks/` stores task contracts (`contract.md`), design notes, `waves.md`, research files (written by `explore` / `architect` or the main agent), briefs, scorecards, and JSONL context. A started task's directory lives in its worktree on branch `arbor/<task>`. Tasks form parent/child trees (`task.py create --parent <slug>`).
- `.arbor/workspace/` stores deliberately written developer journals.
- `.arbor/agents/{explore,architect,test,implement,review,verify,fix,simplify}.md` are role instruction sources (plain markdown, no frontmatter). How they reach the executor is the executor's business (for example one configured assistant per role); the driver itself only passes `{role}` to the executor command.
- A guard hook denies the built-in Agent/Task tool for Arbor roles. A session whose first prompt starts with `Active task:` plus `Role:` is a dispatched role and must not run `arbor.py`, push, merge, or call `task.py start/current/finish`.
- Bundled multi-file skills (`arbor-meta`, `arbor-spec-bootstrap`) are written to `.claude/skills/` and `.starFactory/skills/` by `arbor init` and refreshed by `arbor update`.
- Platform `settings.json` files decide which hooks actually run.
- `.arbor/.template-hashes.json` and `.arbor/.runtime/` are management/runtime state files. Confirm necessity before editing them.

## Do Not

- Do not treat Arbor upstream source code as the default target for local customization.
- Do not modify the global npm install directory or `node_modules` to implement project needs.
- Do not overwrite user-modified local files with default templates; check `.arbor/.template-hashes.json` first and prefer `.new` sidecar files over destructive overwrites.
- Do not put team-private project rules into a bundled skill; put them in `.arbor/spec/`, a project-local skill, the current task, or the workspace journal. `arbor update` overwrites anything inside a bundled skill directory.
- Do not look for or create `.claude/agents/` or `.starFactory/agents/` files for Arbor roles; edit `.arbor/agents/<role>.md` and refresh the executor's copy of it.
- Do not edit content outside the managed `<!-- ARBOR:START -->` / `<!-- ARBOR:END -->` block of `CLAUDE.md` or `AGENTS.md` through Arbor tooling; user text outside the block is theirs.
- Do not describe removed or never-shipped mechanisms as current Arbor behavior; cross-check against the local `.arbor/config.yaml` and `arbor --help` before claiming a knob exists.
