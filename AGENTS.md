# Arbor Instructions

**First decide which agent you are.**

1. **Dispatched sub-agent**: your first prompt begins with `Active task: <path>` and `Role: explore|architect|test|implement|review|verify|fix|simplify` (plus `Mode:` for review, `Range: <base>..<head>`, `Dispatch: d-NNN`, and with codeg MCP a `Prompt: <file>` line: read that file first, it holds the full prompt).
   Do that role directly, using the context already inlined in the prompt (marker `<!-- arbor-hook-injected -->`). If the marker is missing, read `<task>/implement.jsonl` (architect, test, implement) or `<task>/check.jsonl` (review, verify, fix, simplify) and every file it lists, then `contract.md`, `design.md` and `waves.md` if present, and `git diff <Range>`, from the **absolute** task path given. Stay inside your role's write boundary; writers commit on the current branch as `<role>(<task>): <summary>` with trailer `Arbor-Dispatch: <Dispatch>`. Never run `arbor.py` or `task.py start/current/finish`, never push, merge, rebase or switch branches, never write under `.arbor/` outside the task directory. The test role may run Git lifecycle operations only in test-owned disposable repositories under the isolation rules in `.arbor/agents/test.md`; this exception never applies to real project repositories. Report in the format your role instructions define.
2. **Main agent**: anything else. Follow `.arbor/workflow.md`; specs in `.arbor/spec/`; tasks in `.arbor/tasks/`; journals in `.arbor/workspace/`. Simple changes (at most 2 files, cause known, no design choice) do not use Arbor. Otherwise propose a tier (light / standard / full), write and get approval for `contract.md` (research before start with `arbor.py run --role explore|architect|review`, brief at the `brief_path` from `arbor.py next --json`; several independent angles may run concurrently with `next --role <role> --json` and `run --role <role> --dispatch <id>`, no quota), split multi-deliverable requests into a parent plus child tasks (`task.py create --parent`), run `task.py start <task>`, then drive the loop yourself: `python3 ./.arbor/scripts/arbor.py --task <task> next` → do the one thing it names → `next` again (`brief`: write it at `brief_path`, then `arbor.py run`; `run`: `arbor.py gate`; `decide`: `arbor.py decide <choice> --reason "…"`; `human`: `approve_contract` → contract re-approval + `resume`, `plausible` → ask the user, `decide fix|skip`, `stop` → `resume`/`override`/`abandon`, `merge_conflict` → hand-merge + `resume`, `merge` → the user merges `--no-ff`, then `arbor.py finish`). Each child task is driven from its own session; `arbor.py --task <parent> children` lists child tasks; merge them in order and review the merged range with `arbor.py --task <parent> run --role review --mode sweep --range <before>..<base>`. With the default `codeg` executor (`type: codeg-mcp`) a dispatch returns `needs=delegation`: call codeg MCP `delegate_to_agent` with the returned `mcp.arguments` (header plus `Prompt:` pointer), `arbor.py bind --request <path> --task-id <id>`, poll `get_delegation_status`, save the terminal JSON at the returned result_path outside the task worktree and `arbor.py collect --request <path> --result <file>`; resume/poll bound tasks after interruptions. Claude Code and Codex both use this same MCP flow. Never perform a role yourself or use native Agent/Task/spawn_agent for one. Prefer `/arbor:workflow`, `/arbor:continue`, `/arbor:finish-work` when available.

Managed by Arbor. Edits outside this block are preserved; edits inside may be overwritten by `arbor update`.
