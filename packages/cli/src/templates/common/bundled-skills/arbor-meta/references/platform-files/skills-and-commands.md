# Skills And Commands

Skills and commands are textual entry points for user interaction with Arbor. Different platforms use different names, but their core purpose is the same: tell the AI how to enter the Arbor flow when the user expresses a certain intent.

## Conceptual Differences

| Type | Trigger mode | Best for |
| --- | --- | --- |
| skill | AI auto-match or explicit user mention | Long-term capabilities, workflow rules, modification guides. |
| command | Explicit user invocation (`/arbor:<name>`) | Clear operation entry points: `start`, `continue`, `finish-work`, `dispatch-target`. |

Arbor workflow skills share one semantic set: brainstorm, before-dev, check, update-spec, break-loop. Multi-file bundled skills (`arbor-meta`, `arbor-spec-bootstrap`) use layered references.

## Paths

| Platform | Skills | Commands |
| --- | --- | --- |
| Claude Code | `.claude/skills/` | `.claude/commands/arbor/` |
| StarFactory | `.starFactory/skills/` | `.starFactory/commands/arbor/` |

`CLAUDE.md` and `AGENTS.md` carry only the managed Arbor block, not skills. In a user project, use the files actually generated by init as authoritative.

## Skill Structure

A common skill is a directory:

```text
arbor-meta/
├── SKILL.md
└── references/
```

`SKILL.md` should tell the AI:

- When to use this skill.
- Which reference to read first for the current task.
- What not to do.

References hold longer explanations so the entry file does not contain everything.

## Command Structure

Commands are single files. Their content should include:

- When to use it.
- Which `.arbor/` files to read.
- Which scripts to run.
- How to report after completion.

They should not store task state; task state belongs in `.arbor/tasks/` and `.arbor/.runtime/`.

## Local Change Scenarios

| User need | Edit location |
| --- | --- |
| Change AI auto-trigger rules | The corresponding skill's frontmatter description. |
| Change user command behavior | The corresponding command file. |
| Add a project-local skill | `.claude/skills/` and/or `.starFactory/skills/`. |
| Use one capability on both platforms | Write equivalent skills in both skill directories. |
| Change finish/continue entry points | Platform command files under `commands/arbor/`. |

## Modification Principles

1. **Keep entry files short; references carry long content**. This matters especially for multi-file skills like `arbor-meta`.
2. **Make trigger descriptions specific**. A description that is too broad can mis-trigger; one that is too narrow may not trigger.
3. **Keep the same semantics consistent across both platforms**.
4. **Put project-specific capabilities in local skills**. Do not put team-private flows into public `arbor-meta`.

If the user only wants local AI to know one more project rule, usually create a project-local skill or update `.arbor/spec/` instead of changing a Arbor built-in workflow skill.
